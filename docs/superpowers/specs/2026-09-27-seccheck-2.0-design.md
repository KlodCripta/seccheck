# SecCheck 2.0 — agreed design

The user approved a stronger terminal application for Arch Linux and derivatives,
English/Italian selection at startup, understandable findings for non-experts,
and the Petrolio visual proposal. Implementation was authorized on 2026-09-27.

## Product and packaging

- Keep the MIT license and a standalone Bash entry point `seccheck.sh`.
- Bash 4.4+, Arch identification plus pacman; no assumption that systemd is present.
- Interactive language menu: 1 English, 2 Italiano. All authored interface and
  explanations use the chosen language; upstream evidence stays verbatim and labelled.
- CLI: --lang en|it, --scan full|rkhunter|lynis|integrity|aur, --no-color,
  --ascii, --demo [scenario], --help, --version. Noninteractive scans require --lang.
- Root is requested only for an actual scan, retaining options and invoking identity.
- Dependencies are explained per module; a missing optional scanner does not prevent
  using other modules. Installation is an explicit menu action with pacman confirmation.

## Evidence and assessment

- Each module has status not-run/running/completed/partial/failed/skipped, a reason,
  exit status, version and raw evidence. No-output failures and unknown formats never
  produce a clean result. Coverage concerns selected modules, with overall scope stated.
- Findings carry module, kind, priority, confidence, object, explanation/action keys,
  source evidence and a stable deduplication key. No user-controlled field is executed.
- Kinds distinguish suspicious indicators, package integrity and hardening suggestions.
- The strongest unresolved finding drives priority; configuration advice does not
  corroborate unrelated malware indicators. No compromise probability or safety score.
- AUR cache references mean possible exposure, matching known SHA-256 means presence
  of known bytes, and neither alone proves execution. Rootkit signatures remain open
  until specifically resolved. A package metadata match is not a malware clearance.
- Display coverage and urgency separately, including simultaneous urgent + incomplete.
- Detailed checks update findings without overriding stronger evidence or hiding
  unexamined findings. All findings remain in reports even if screen output is limited.

## Scanners

- rkhunter: fixed command locale, capture stdout/stderr and a fresh detailed log,
  require a completion marker, parse warnings and useful continuation lines. Updating
  signatures is explicit and its actual result is reported; never call --propupd.
- Lynis: consume its fresh report-data file and test identifiers; preserve warnings,
  suggestions and raw report, verify report completion and scanner return code.
- Integrity: pacman -Qkk metadata plus paccheck SHA-256 (pacutils), clearly distinguish
  unavailable hashes from success. A changed executable is never dismissed as normal
  merely because its size or timestamp changed. Backup/configuration files are labelled.
- AUR: bundled, sourced and dated Atomic Arch indicators; collect foreign package
  inventory/history, statically inspect known AUR/npm/Bun cache and installation roots,
  system/user autostart definitions, selected candidate files and known eBPF map names.
  Read-only, no sourcing PKGBUILDs, executing payloads, cleaning, updating AUR packages,
  fetching code, or sending local data. Honour invoking user's home and other local
  homes, report unreadable paths, file/time bounds and deliberately excluded areas.
- Indicators ship with SecCheck releases. No unverified live feed or claim to cover
  every campaign. Retain source dates and limitations in the report.

## Terminal and reporting

- Petrolio/cyan accents, neutral text, thin rules, aligned module table, counts per
  finding type and completed-module bar; no arbitrary percentages of security.
- Keep a labelled traffic light for priority. Grey represents incomplete coverage.
- Text labels accompany colors; honour NO_COLOR, dumb terminals, ASCII and narrow widths.
- Show plain-language next steps; menu permits detailed findings, report and rescan.
- Plain-text reports, raw files and a machine-readable TSV use a private run directory.
  Escape control sequences in displayed evidence and TSV; never eval/source report data.
- Provide demonstrative scenarios, clearly labelled and usable without root/dependencies.

## Validation and limits

## Approved extension: AUR project maintenance (28 September, Europe/Rome)

The user requested checking every installed AUR package for outdated/orphaned or
apparently abandoned projects and changes/additions to maintainers. Add a separate
`aur-health` module, included in full scans, with online AUR metadata and an explicit
`--offline` option. Explain that this query sends foreign package names to AUR.
The preceding no-network requirement continues to apply to static Atomic Arch checks.

- Query installed foreign packages through the official AUR RPC; a foreign package
  absent from AUR is not automatically a removed AUR package.
- Distinguish an installed version behind AUR, an upstream out-of-date flag, no
  maintainer, and an old last-modified timestamp. Never assert abandonment from age
  alone; report the elapsed time, with a documented 365-day review threshold.
- Record current maintainers and co-maintainers when authoritatively available.
  Compare later successful snapshots. First observations establish a baseline, not
  proof of a safe maintainer; historical changes before that baseline are unknown.
- Failed/offline/invalid responses cannot mean removed packages or clean coverage,
  and must not replace a valid baseline. All observed changes stay in the run report.
- Document API/source limitations instead of fabricating unavailable history.

## Validation and limits (continued)

- Regressions for empty failed scans, unprocessed high warnings, pacman size changes,
  selected-only scans, missing tools, duplicate evidence, translation and narrow output.
- Integration fixtures follow upstream formats; command-boundary doubles are necessary
  because the execution host is Ubuntu and has no Arch scanners installed.
- Tests must never modify host packages, access private user data or delete production logs.
- Deliver as a reviewable development version. Do not merge, tag a stable release or
  update AUR; native Arch and derivative validation remains necessary before publishing.
